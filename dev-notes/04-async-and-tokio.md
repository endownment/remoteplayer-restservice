# 04. Асинхронность, Tokio, каналы и акторы

## async/await

Модель похожа на `Task`/`async` в .NET, с одним важным отличием: future в Rust
**ленивая**. `async fn` возвращает объект-состояние, и он ничего не делает,
пока его не начнут опрашивать (`.await` или `tokio::spawn`). В .NET Task
запускается сразу.

Исполнитель (runtime) не встроен в язык — им служит библиотека **Tokio**.
`#[tokio::main]` разворачивается в обычный `main`, который создаёт runtime
(пул потоков и epoll) и блокируется на нашей future.

- restservice: многопоточный runtime (у Pi 3 четыре ядра, а запросы идут параллельно);
- mpvwatcher: `flavor = "current_thread"`, одного потока хватит на опрос раз
  в 7 секунд, и памяти он ест меньше.

## Задачи (tasks)

`tokio::spawn(future)` — лёгкая «зелёная» задача, ближе всего к виртуальным
потокам Java 21. Их тысячи, они дешёвые. Задача обязана быть `Send + 'static`:
её могут перенести на другой поток, и она не может ссылаться на чужой стек.
Поэтому в задачу **перемещают** (`move`) данные или `Arc`-клоны.

## Блокирующий код: `spawn_blocking`

Асинхронный поток нельзя блокировать надолго: на нём ждут другие задачи. Если
работа долгая и синхронная (MD5 гигабайтного файла, ioctl CEC с ожиданием
ответа до секунды, `fsync` на SD-карте), её выносят в отдельный пул:

```rust
tokio::task::spawn_blocking(move || md5_cache::md5_with_cache(&path)).await
```

## `std::sync::Mutex` или `tokio::sync::Mutex`

- `std::sync::Mutex`/`RwLock` — быстрые, но держать их через `.await` нельзя
  (поток уснёт с захваченной блокировкой). Используются, когда критическая
  секция короткая и синхронная: `SettingsStore::current`, журнал
  дочернего процесса.
- `tokio::sync::Mutex` — асинхронный, его можно держать через `.await`.
  `player_operation` в `AppContext` держится всё время перезапуска mpv
  (секунды), поэтому он из tokio. `try_lock` даёт ответ 409 «уже идёт
  другая операция» вместо очереди.

## Каналы

| Канал | Семантика | Где используется |
|---|---|---|
| `mpsc` | много отправителей → один получатель, очередь | запросы к актору mpv, команды супервизору процесса |
| `oneshot` | одно значение, один раз | ответ на конкретный запрос |
| `broadcast` | одно сообщение → всем подписчикам, отстающие теряют старое | события mpv → все WebSocket-клиенты |
| `watch` | хранит **последнее** значение, подписчики видят изменения | состояние подключения к mpv |

## Актор: владелец ресурса за каналом

`MpvClient` (`src/mpv/client.rs`) — это не объект с сокетом внутри, а
**ручка**. Сокетом владеет одна задача, `ConnectionTask`:

```
 обработчик HTTP ──mpsc(PendingRequest{line, oneshot})──▶ ConnectionTask ──▶ сокет mpv
        ▲                                                  │  ▲
        └──────────────── oneshot (ответ) ─────────────────┘  │
 WebSocket ◀──── broadcast (события) ──────────────────────────┘
 lifecycle ◀──── watch (Connected{generation} / Disconnected)
```

- Номера запросов (`request_id`) раздаёт ручка атомарным счётчиком.
  Актор хранит `HashMap<request_id, oneshot::Sender>` и, получив строку с
  ответом, отдаёт её тому, кто ждёт.
- Мьютекса вокруг сокета нет: к сокету прикасается только актор.
- При обрыве актор отвечает всем ждущим `ConnectionLost`, сообщает
  `Disconnected` и раз в 0,5 с пытается переподключиться. Каждое новое
  подключение получает `generation + 1`. По этому номеру `lifecycle` понимает,
  что mpv действительно перезапустился.

Тот же приём — у `ChildProcessManager`: супервизор владеет `Child`.

## `select!` — ждать нескольких событий сразу

```rust
let wakeup: Wakeup = tokio::select! {
    request = self.requests.recv() => Wakeup::Request(request),
    line = lines.next_line() => Wakeup::Line(line),
};
match wakeup { ... }
```

`select!` ждёт первую готовую future, а остальные **отменяет** (уничтожает).
В коде это всегда делается в два шага: `select!` только решает, что случилось
(возвращает enum), а реакция — отдельный `match` после него. Так заимствования,
которые держат обе future, заканчиваются до того, как мы меняем состояние, и
borrow checker доволен.

Важно для отмены: `recv()` у каналов и `next_line()` безопасны при отмене
(cancel-safe), данные при этом не теряются. Это одно из условий, которые
стоит проверять в документации, прежде чем класть future в `select!`.

## Отмена = уничтожение future

В Rust нет `CancellationToken` как обязательного механизма: чтобы отменить
future, её просто уничтожают. Отсюда два следствия, на которые опирается код:

1. Таймаут — это `tokio::time::timeout(limit, future)`: по истечении времени
   внутренняя future уничтожается.
2. Очистка при отмене делается через `Drop` (см. `PartialFile` в
   [03](03-ownership-in-this-code.md)), а не через `finally`.
