# 02. Rust для разработчика с опытом ООП

ООП-опыт пригодится, просто не напрямую. Часть привычек переносится почти
дословно, часть заменяется более строгими механизмами. Ниже — словарь.

## Классы → `struct` + `impl`

```rust
pub struct MediaLibrary {            // поля: только данные
    canonical_root: PathBuf,
    default_folder: EntryName,
}

impl MediaLibrary {                  // методы: отдельным блоком
    pub fn open(config: &StorageConfig) -> Result<MediaLibrary, StorageError> { ... }   // «конструктор»
    pub async fn list_files(&self, folder: &EntryName) -> ... { ... }                   // метод экземпляра
}
```

- Конструкторов нет. Принято писать ассоциированную функцию `new`/`open`/
  `load`, которая возвращает `Self` или `Result<Self, E>`, если создание
  может провалиться. Вспомни фабричный метод в Java.
- `&self` — как `this` в C++ для константного метода; `&mut self` — неконстантный
  метод; `self` (без `&`) — метод, который **поглощает** объект (после вызова
  объекта больше нет, см. [03](03-ownership-in-this-code.md)).
- Видимость: всё приватно по умолчанию; `pub` — публично. Граница
  приватности — **модуль**, а не тип: функции того же модуля видят приватные
  поля. Это ближе к package-private в Java, чем к private в C++.

## Наследования нет

У структур нет базовых классов. То, ради чего обычно наследуются, делается
так:

| Зачем наследовались | Что в Rust |
|---|---|
| общий интерфейс | `trait` (интерфейс) |
| переиспользование кода | композиция: поле с другой структурой |
| закрытая иерархия вариантов (Shape → Circle, Rect) | `enum` с данными |
| значения по умолчанию в методах | методы по умолчанию в `trait` |

## Интерфейсы и полиморфизм

**Открытый набор реализаций** (код пишут другие, наперёд не известен) — это
`trait`. Он похож на интерфейс Java/C#. Вызов идёт либо статически, через
дженерики (как шаблоны C++: код генерируется под каждый тип), либо динамически,
через `dyn Trait` (как виртуальные функции: vtable).

**Закрытый набор** (все варианты известны, их немного) — это `enum`. Пример
из кода:

```rust
pub enum ServiceManager {
    Systemd(SystemdUnitManager),
    ChildProcess(ChildProcessManager),
}

impl ServiceManager {
    pub async fn restart(&self, mpv_args: Vec<String>) -> Result<(), ServiceError> {
        match self {
            ServiceManager::Systemd(manager) => manager.restart().await,
            ServiceManager::ChildProcess(manager) => manager.restart(mpv_args).await,
        }
    }
}
```

Почему так, а не `trait ServiceManager` + `Box<dyn ServiceManager>`:

- `match` обязан перечислить **все** варианты. Добавишь третий — компилятор
  покажет каждое место, которое его не обрабатывает. В Java такого нет до
  sealed interfaces + pattern matching (Java 21), и это очень похоже на них.
- Никаких аллокаций в куче и виртуальных вызовов.
- Async-методы в `dyn Trait` пока требуют обходных путей (крейт
  `async-trait` или ручной `Box<dyn Future>`), а с `enum` их не нужно.

Trait объекты разумны там, где реализации действительно подключаются извне
(плагины, библиотеки). Здесь это «настоящее железо | заглушка» — закрытый
набор.

## Enum — это не «enum из C»

В C и Java enum — набор именованных констант. В Rust каждый вариант может
нести **свои данные** (это называется sum type / tagged union). Пример —
команды плеера (`src/player_command.rs`):

```rust
pub enum PlayerCommand {
    Play { folder: String, name: String, mode: LoadMode },
    Seek { seconds: f64, mode: SeekMode },
    Pause,
    ...
}
```

В ООП это была бы иерархия классов Command с подклассами и паттерн Visitor.
Здесь это одно перечисление и один `match`. serde даже разбирает его из JSON
по полю `type` (`#[serde(tag = "type")]`).

## null → `Option<T>`, исключения → `Result<T, E>`

- `null` нет. Значение, которого может не быть, имеет тип `Option<T>`:
  либо `Some(value)`, либо `None`. Компилятор не даст использовать его, не
  проверив. NullPointerException в Rust не бывает.
- Исключений нет. Функция, которая может провалиться, возвращает
  `Result<T, E>`: `Ok(value)` или `Err(error)`. Оператор `?` пробрасывает
  ошибку наверх, это аналог `throws` с автоматическим rethrow. Подробнее в
  [05-errors.md](05-errors.md).
- `panic!` существует, но означает «баг, программа не может продолжать», а не
  штатную ошибку. В коде сервиса паник нет; `expect` встречается только в
  тестах.

## Обобщённые типы

`Patch<T>` (`src/settings/patch.rs`) — обобщённый enum, как шаблон класса в
C++ или generic в Java. Отличия:

- Как и в C++, код генерируется под каждый конкретный `T` (мономорфизация),
  стирания типов, как в Java, нет.
- Ограничения на `T` пишутся явно: `impl<T: Clone> Patch<T>`. Это как
  `<T extends Comparable<T>>` в Java или concepts в C++20. Без ограничения
  нельзя вызвать у `T` ни одного метода; ошибки шаблонов «на 500 строк», как в
  C++, не бывает.

## Аннотации → атрибуты и derive-макросы

`#[derive(Debug, Clone, Serialize, Deserialize)]` — ближайший аналог аннотаций
Lombok/Jackson. Это макросы времени компиляции: они генерируют реализации
трейтов (`Debug` — печать, `Clone` — копирование, `Serialize` — в JSON). Без
рефлексии во время выполнения: всё развёрнуто в обычный код.
`#[serde(rename_all = "kebab-case")]` настраивает этот сгенерированный код,
как `@JsonProperty`.

## Пакеты и сборка

| Java / .NET | Rust |
|---|---|
| Maven/Gradle, NuGet | Cargo |
| `pom.xml` / `.csproj` | `Cargo.toml` |
| lock-файл (Gradle) | `Cargo.lock` (в приложениях коммитится) |
| артефакт / сборка | crate |
| package / namespace | module (`mod`) |
| Maven Central / NuGet.org | crates.io |
| JUnit | встроенный `#[test]` + `cargo test` |

Модули объявляются явно: `mod storage;` в `main.rs` подключает
`src/storage/mod.rs`. Тесты по соглашению лежат в том же файле, в модуле
`#[cfg(test)] mod tests` — они видят приватные функции и не попадают в
релизную сборку.

## Чего нет и не надо

- **Геттеров/сеттеров на всё.** Поля, которые можно читать, просто `pub`.
  Инварианты защищает тип: например, `EntryName` можно создать только через
  `EntryName::parse`, поэтому невалидного имени не существует.
- **DI-контейнера.** Зависимости собираются вручную в `AppContext::initialize`
  и передаются через `Arc<AppContext>`. Это та же инверсия зависимостей, только
  без магии: видно, кто кого создаёт.
- **Синглтонов со статикой.** Глобальное изменяемое состояние в Rust
  намеренно неудобно; вместо него — один контекст, переданный явно.

## Где ООП-практики честно работают

- **Value object / newtype** — `EntryName`, обёртка над `String`, которая
  гарантирует валидность. В Rust это очень дешёвый и идиоматичный приём.
- **Принцип единственной ответственности, слои** — модули выше.
- **RAII** (это из C++, а не из ООП в целом) — центральная идея Rust.
  `PartialFile` в `storage/upload.rs` удаляет недокачанный файл в `Drop`.
- **Command pattern** — как enum, см. выше.
- **Actor** — владелец ресурса за каналом, см. [04](04-async-and-tokio.md).
