# 06. mpv IPC: клиент, состояние, снимок и восстановление

## Протокол

`--input-ipc-server=/run/remoteplayer-mpv/mpv.sock` открывает unix-сокет. По
нему в обе стороны ходят JSON-объекты, по одному на строку (`man mpv`, раздел
JSON IPC):

```
→ {"command": ["get_property", "volume"], "request_id": 7}
← {"data": 100.0, "request_id": 7, "error": "success"}
← {"event": "property-change", "id": 3, "name": "pause", "data": true}
```

- Ответы приходят вперемешку с событиями. Отличить их можно только по полям:
  `event` — событие, `request_id` — ответ (`src/mpv/protocol.rs`).
- `error` бывает не только `"success"`. Например, `"property unavailable"` для
  `duration` в режиме простоя — это нормальное «значения сейчас нет», поэтому
  у клиента есть `get_property_optional`, который вернёт `Ok(None)`.
- `observe_property <id> <name>` подписывает **текущее соединение** на
  изменения свойства. После переподключения подписку нужно оформить заново,
  и актор делает это сам.
- К сокету может подключиться сколько угодно клиентов: restservice,
  mpvwatcher, jellyfin-mpv-shim. Каждый получает свои ответы и свои события.
  Ничто в коде не предполагает, что мы у mpv единственные: состояние никогда
  не кешируется, а каждый раз спрашивается или приходит событием.

## Два клиента — и почему они разные

- **restservice** (`src/mpv/client.rs`) — актор с одним постоянным
  соединением: параллельные запросы от многих HTTP-обработчиков, события для
  WebSocket, автоматическое переподключение. См. [04](04-async-and-tokio.md).
- **mpvwatcher** — простейший последовательный клиент: отправил, дождался
  своего `request_id`, следующий. Первой командой он выполняет
  `disable_event all`, чтобы события не мешали. Делать сложнее, чем нужно,
  незачем.

## Снимок состояния (`PlayerSnapshot`)

Что сохраняется и почему именно это:

| Поле | Свойство mpv | Зачем |
|---|---|---|
| `playlist` | `playlist` (`filename`, `title`) | весь плейлист, а не только текущий файл |
| `playlist-pos` | `playlist-pos` (-1 → нет) | какой элемент играл |
| `time-pos` | `time-pos` | позиция в текущем файле |
| `paused` | `pause` | восстанавливать в паузе, если было в паузе |
| `volume`, `muted`, `speed` | `volume`, `mute`, `speed` | |
| `audio-track`, `subtitle-track`, `secondary-subtitle-track` | `aid`, `sid`, `secondary-sid` | выбранные дорожки |
| `audio-delay`, `subtitle-delay` | `audio-delay`, `sub-delay` | ручная синхронизация |

Тонкость с `aid`. Если mpv не смог открыть аудиовыход (неверный
`audio-device`, HDMI-приёмник выключен), он сам снимает выбор аудиодорожки, и
`aid` читается как `false`. Если это сохранить и восстановить, звук не вернётся
и после исправления устройства. Поэтому «нет дорожки» при отсутствии
`current-ao` записывается как `auto` (`read_audio_track`). Нашлось это при
живой проверке в контейнере без звуковой карты.

## Восстановление

`PlayerSnapshot::restore_commands` — чистая функция (без ввода-вывода),
поэтому последовательность проверяется юнит-тестом:

```
stop                                        # пустой плейлист
set_property pause <paused>                 # до загрузки: файл сразу начнёт в нужном состоянии
set_property volume / mute / speed / audio-delay / sub-delay
loadfile <file1> append -1 ""               # все элементы — без запуска
loadfile <file2> append -1 "start=83.250,aid=2,sid=no,secondary-sid=no"   # опции только у текущего
set_property playlist-pos 1                 # запускает нужный файл; его опции срабатывают
```

- Синтаксис `loadfile <url> <flags> <index> <options>` появился в **mpv 0.38**:
  добавился аргумент `index` (-1 — по умолчанию). Проект нацелен на mpv 0.40
  из trixie. На mpv 0.37 команда отклоняется с `invalid parameter`, и это
  честно приходит в `restore-warnings`.
- `append` при `--idle=yes` и пустом плейлисте не начинает воспроизведение — в
  отличие от `append-play`. Поэтому сначала собирается весь плейлист, а затем
  одним `playlist-pos` выбирается нужный элемент.
- Опции файла (`start=`, `aid=`...) действуют только на этот элемент
  плейлиста и применяются, когда он начинает играть. Глобальные свойства
  при этом не меняются.
- Ошибки отдельных команд не прерывают восстановление: они собираются в
  предупреждения. Лучше восстановить громкость и плейлист без позиции, чем
  ничего.

## Перезапуск и восстановление после падения

**Запланированный перезапуск** (`lifecycle::restart_and_restore`):

1. снять снимок у работающего mpv;
2. запомнить номер подключения (`generation`);
3. попросить systemd (или супервизор) перезапустить mpv;
4. ждать подключения с `generation` больше запомненного (таймаут
   `restart-timeout-seconds`); не дождались — ошибка с логом mpv;
5. восстановить снимок.

Флаг `planned_restart` говорит механизму восстановления после падения, что
этот перезапуск наш и вмешиваться не надо.

**Падение** (`lifecycle::watch_for_crashes`): на каждое новое подключение
читается `pid` mpv. Если он сменился, а перезапуск не наш, берётся снимок
mpvwatcher. Восстановление идёт, только если:

- снимок записан **тем самым** процессом, который умер (`snapshot.mpv.pid`);
- в снимке есть плейлист;
- новый mpv ещё пуст (`playlist-count == 0`): если пользователь или
  другой IPC-клиент уже что-то запустил, мы этого не трогаем.

Третье условие заодно защищает от гонки: если флаг уже снят, а событие
подключения обработалось позже, mpv к этому моменту уже восстановлен и не пуст.
