# 07. Настройки, systemd, polkit, D-Bus

## Модель настроек

`PlayerSettings` (`src/settings/mod.rs`) — плоская структура: одно поле на
каждую опцию mpv, которой управляет сервис. Ключи в JSON и TOML совпадают с
именами опций mpv: `audio-device` — это `--audio-device`.

Метод `entries()` описывает каждую опцию: ключ, значение, способ применения
(`Runtime` / `Restart`), обязательна ли она. На этом описании построено всё
остальное: проверка значений, вычисление изменений (`changes_to`), сборка
аргументов командной строки (`to_mpv_args`), список способов применения в
`GET /settings`. Новая настройка — это одно поле, одна строка в `entries()`,
одна строка в `with_patch` и одна в `builtin_defaults`.

## PATCH и PUT: JSON Merge Patch

Каждое поле `SettingsPatch` имеет тип `Patch<T>`:

| В JSON | `Patch` | Результат |
|---|---|---|
| ключа нет | `Keep` | текущее значение |
| `null` | `Reset` | значение по умолчанию |
| значение | `Set(v)` | `v` |

Различить «ключа нет» и «`null`» стандартный `Option<T>` не может. Поэтому
`Patch<T>` реализует `Deserialize` вручную, а на структуре стоит
`#[serde(default)]`: serde вызывает десериализатор поля только для
присутствующих ключей, а для отсутствующих берёт `Default` (= `Keep`).

- `PATCH` = `текущие.with_patch(patch, умолчания)`
- `PUT` = `умолчания.with_patch(patch, умолчания)`: всё, чего нет в теле,
  становится значением по умолчанию — это и есть исходное «если параметр
  отсутствует, используется дефолт».

Тот же тип читает `[player-defaults]` из конфигурации и сохранённый
`settings.json`. Благодаря этому настройка, добавленная в новой версии, в
старом файле просто получает своё значение по умолчанию.

## Применение (`lifecycle::apply_settings`)

1. Проверить новые значения и вычислить изменения. Ничего не изменилось —
   ответ сразу.
2. Записать новый `mpv.env` (старый текст сохранить для отката).
3. Есть изменение класса `Restart` → один перезапуск с восстановлением
   состояния. Не получилось — записать старый `mpv.env`, перезапустить с
   ним и вернуть 502 с логом mpv. «Не получилось» означает одно из двух:
   - mpv не открыл сокет за `restart-timeout-seconds` — так бывает при
     неизвестной опции или неверном значении (`--fullscreen=maybe`,
     `--demuxer-max-bytes=abc`), mpv тогда сразу завершается;
   - при `force-window=yes` свойство `current-vo` не появилось за 5 секунд.
     Нерабочий `vo`, `gpu-context` или DRM-плоскость mpv переживает молча:
     процесс жив, сокет открыт, но окна нет. Это нашлось на живой проверке:
     одного ожидания сокета мало.
4. Только `Runtime`-изменения → `set_property` для каждой, без перезапуска.
   Если mpv отклонил значение, уже применённые изменения этого запроса
   возвращаются назад, `mpv.env` восстанавливается, и клиент получает 422.
   Иначе неверное значение попало бы в `mpv.env` и не дало бы mpv
   стартовать в следующий раз, причём откат вернул бы тот же испорченный файл.
   Если mpv не запущен, проверить значение не на чем: оно ложится в
   `mpv.env` до следующего старта, а при ошибке сработает пункт 3.
5. Сохранить `settings.json` (атомарно: временный файл + `fsync` + `rename`).

Операции перезапуска и изменения настроек сериализуются мьютексом
`player_operation`. Второй одновременный запрос получает 409.

## EnvironmentFile вместо генерации unit-файла

Исходная идея — генерировать unit-файл из параметров. Почему от неё ушли:

- Писать в `/etc/systemd/system` и делать `daemon-reload` может только root.
  Через polkit для этого пришлось бы выдать `manage-unit-files`, а это право
  не ограничивается одним юнитом. С ним сервис мог бы подложить юнит с
  `User=root`, то есть фактически получил бы root.
- Генерация unit-файла заодно позволяет менять «как» запускается mpv
  (пользователь, группы, песочница), а настройкам это не нужно.

Поэтому unit статичен, а меняется только файл окружения:

```ini
EnvironmentFile=-/var/lib/remoteplayer/mpv.env
ExecStart=/usr/bin/mpv --no-terminal --idle=yes --input-ipc-server=... $REMOTEPLAYER_MPV_ARGS
```

```sh
# /var/lib/remoteplayer/mpv.env (пишет сервис)
REMOTEPLAYER_MPV_ARGS='--audio-device=alsa/hdmi:CARD=vc4hdmi,DEV=0 --vo=gpu --gpu-context=drm ...'
```

`$VAR` **без фигурных скобок** systemd разбивает по пробелам на отдельные
аргументы (`man systemd.service`, раздел «Command lines»), а `${VAR}` дал бы
один аргумент. Отсюда правило валидации: в значениях запрещены пробелы,
кавычки, `\`, `$`, обратная кавычка, иначе значение могло бы протащить лишний
аргумент вроде `--script=/tmp/evil.lua`. Это проверяет тест
`whitespace_cannot_inject_extra_arguments`.

mpv запускается только с опциями командной строки, без отдельного
конфигурационного файла. Каждый IPC-клиент видит один и тот же явно
сконфигурированный mpv, а опции командной строки имеют приоритет над любым
`mpv.conf`, если он у пользователя есть.

## D-Bus через zbus

`src/service_manager/systemd.rs`:

```rust
#[zbus::proxy(interface = "org.freedesktop.systemd1.Manager",
              default_service = "org.freedesktop.systemd1",
              default_path = "/org/freedesktop/systemd1")]
trait SystemdManager {
    fn restart_unit(&self, name: &str, mode: &str) -> zbus::Result<OwnedObjectPath>;
}
```

Макрос генерирует из трейта клиентскую структуру `SystemdManagerProxy` с
async-методами. Метод `restart_unit` превращается в вызов D-Bus `RestartUnit`.
Это примерно как генерация клиента из WSDL/gRPC, только из описания прямо в
коде. Документация интерфейса: `man org.freedesktop.systemd1`.

- `RestartUnit` возвращает путь к задаче (job) сразу, не дожидаясь
  перезапуска. Дождаться готовности mpv надёжнее по его сокету, поэтому сервис
  ждёт новое подключение IPC, а не окончания задачи systemd.
- Свойства юнита (`ActiveState`, `UnitFileState`, `MainPID`) читаются без
  кеша (`CacheProperties::No`): прокси живёт один запрос и сигналов об
  изменениях не дождётся.
- zbus написан на чистом Rust, поэтому не нужны `libdbus` и заголовки при
  сборке на Pi.

## polkit

`deploy/polkit/50-remoteplayer.rules` разрешает пользователю `coop`:

- `org.freedesktop.systemd1.manage-units` для `unit == remoteplayer-mpv.service`
  и `verb` из `start`/`stop`/`restart`;
- `org.freedesktop.login1.reboot` / `power-off` (и варианты `-multiple-sessions`).

Больше ничего. В отличие от `sudo`, это работает при `NoNewPrivileges=yes`
(D-Bus-вызов — не смена привилегий процесса) и не требует запускать внешние
программы.

Автозапуск (`enable`) остаётся шагом установки: `EnableUnitFiles` требует
`manage-unit-files` — см. выше, почему его выдавать нельзя. `GET
/player/service` показывает текущий `UnitFileState`, так что видно, включён
ли автозапуск.
