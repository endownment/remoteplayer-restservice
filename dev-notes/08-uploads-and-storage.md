# 08. Файлы: библиотека, загрузка, MD5

## Структура

```
upload-root/            ← в корень файлы не пишутся
├── inbox/              ← default-folder: сюда идёт POST /uploads без ?folder=
├── movies/
└── series/
```

Вложенных папок нет — это требование. БД нет: файлы могут появляться и
другими путями (scp, USB), поэтому источник истины — сама файловая система.

## Имена: `EntryName`

`src/storage/names.rs` — newtype над `String`. Создать его можно только через
`EntryName::parse`, который отвергает пустые имена, `/`, `\`, управляющие
символы, начальную точку (а значит `.`, `..` и скрытые файлы) и имена длиннее
255 байт. Все функции библиотеки принимают `&EntryName`, а не `&str`, поэтому
непроверенное имя до файловой системы физически не доходит. Это проверяет
компилятор, а не код-ревью.

Вторая линия защиты — симлинки. Папку мог вручную сделать ссылкой кто
угодно, поэтому путь канонизируется (`canonicalize`) и проверяется
`starts_with(canonical_root)`. Есть тест: ссылка наружу даёт 403.

## Потоковая загрузка (`src/storage/upload.rs`)

У Pi 3 1 ГБ памяти, а фильм весит гигабайты. Поэтому тело запроса никогда не
лежит в памяти целиком:

```
HTTP body (Stream<Bytes>) ──▶ MD5 hasher.update(chunk)
                          └─▶ BufWriter(1 МиБ) ──▶ .имя.part-<pid>-<n>
конец потока: flush → fsync → сверка MD5 → rename в имя → xattr с MD5
```

- `receive_upload` обобщена по типу потока: `S: Stream<Item = Result<Bytes, E>>`.
  Один и тот же код принимает сырое тело `PUT` (`Body::into_data_stream`), часть
  multipart (`Field`) и `stream::iter(...)` в тестах. Это статический
  полиморфизм, как шаблон в C++.
- Временный файл лежит **в той же папке**: `rename` атомарен только в пределах
  одной файловой системы. Имя начинается с точки, поэтому `list-files` его не
  видит, и mpv не начнёт играть недокачанный файл.
- Отмена (клиент ушёл) и любые ошибки обрабатываются одним механизмом:
  `PartialFile::drop` удаляет временный файл, если не было `commit()`. См.
  [03](03-ownership-in-this-code.md#raii-и-отмена-partialfile).
- Место проверяется по `Content-Length` до первого записанного байта: нужно
  `длина + min-free-bytes` свободного места, иначе 507. Если диск всё-таки
  заполнился во время записи, ENOSPC тоже превращается в 507
  (`ErrorKind::StorageFull`).
- axum по умолчанию ограничивает тело 2 МБ. Для маршрутов загрузки ограничение
  снято (`DefaultBodyLimit::disable()`), а лимит `max-upload-bytes`
  проверяется по ходу записи.
- Перезапись — только по `?overwrite=true`; существование файла проверяется до
  начала и ещё раз перед `rename`. Между этими проверками остаётся окно
  гонки: на домашнем устройстве им можно пренебречь, а полностью его
  закрыл бы `renameat2(RENAME_NOREPLACE)`.

## MD5 для «чужих» файлов

`GET .../md5` считает хэш любого файла (в `spawn_blocking`, буфер 1 МиБ) и
кладёт его в расширенный атрибут `user.remoteplayer.md5` вместе с размером и
mtime с наносекундами. Следующий запрос возьмёт значение из атрибута, если
размер и mtime не изменились. Это кеш без БД, и он живёт вместе с файлом,
даже при переименовании. На FAT/exFAT xattr нет: там хэш каждый раз
считается заново, и это не ошибка.
