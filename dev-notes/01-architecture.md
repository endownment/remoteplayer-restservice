# 01. Архитектура

## Компоненты на Pi

```
                 HTTP :8080                       unix socket (JSON IPC)
 клиенты  ───────────────────▶ remoteplayer-restservice ─────────────┐
 (веб, приложения)                 │      ▲                          ▼
                                   │      │ state.json        remoteplayer-mpv.service
                         D-Bus     │      │                     (mpv на DRM, HDMI)
                     (systemd,     │  remoteplayer-mpvwatcher ───────┘
                      logind)      │      (опрос раз в 7 с)          ▲
                                   ▼                                 │
                            systemd  ── EnvironmentFile ── mpv.env ──┘
                                                               (пишет restservice)
                    сторонние IPC-клиенты (jellyfin-mpv-shim) ──────▶ тот же сокет mpv
```

- **mpv** — отдельный systemd-юнит. Сервис его не встраивает и не запускает
  сам: mpv живёт независимо, а сервис — один из клиентов его IPC-сокета.
  Поэтому падение сервиса не останавливает видео, и к тому же mpv могут
  подключаться другие программы.
- **restservice** держит одно постоянное соединение с mpv. Через него идут
  команды и приходят события. Если mpv перезапускается, сервис сам
  переподключается.
- **mpvwatcher** — отдельный маленький процесс. Раз в 7 секунд он сохраняет
  состояние плеера. Если mpv упадёт, systemd его поднимет, а restservice
  восстановит воспроизведение из этого файла.

## Модули `src/`

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `main.rs` | разбор аргументов, логирование, запуск HTTP-сервера, сигналы | всё |
| `app_context.rs` | создаёт и связывает все компоненты (ручной DI) | все модули ниже |
| `config.rs` | TOML-конфигурация и её проверка | `settings` (тип патча) |
| `routes/` | HTTP: маршруты, разбор запросов, сериализация ответов | все доменные модули |
| `error.rs` | единая точка, где доменные ошибки становятся HTTP-статусами | доменные ошибки |
| `auth.rs` | middleware с bearer-токеном | `app_context` |
| `mpv/` | IPC-клиент, протокол, состояние, снимок/восстановление, фильтр сырого IPC | — |
| `settings/` | модель настроек mpv, merge-patch, хранение, EnvironmentFile | `fs_util` |
| `lifecycle.rs` | применение настроек, перезапуск с сохранением состояния, восстановление после падения | `mpv`, `settings`, `service_manager` |
| `service_manager/` | systemd через D-Bus или дочерний процесс (для разработки) | — |
| `storage/` | папки и файлы, загрузка, MD5 | — |
| `player_command.rs` | типизированные команды → команды mpv | `mpv`, `storage` |
| `audio.rs`, `display.rs`, `cec/`, `system_info.rs`, `power.rs` | железо | `mpv` (частично) |

Доменные модули ничего не знают про HTTP. Единственное исключение — `error.rs`:
это граница, на которой ошибки превращаются в статусы. Так модули проще
тестировать и переиспользовать.

## Ключевые решения и их причины

**Настройки mpv лежат не в mpv.conf и не в сгенерированном unit-файле, а в
EnvironmentFile.** Unit-файл статичен, его ставит root. Сервис пишет только
`/var/lib/remoteplayer/mpv.env`, а systemd подставляет оттуда
`$REMOTEPLAYER_MPV_ARGS` в `ExecStart`. Если бы сервис сам писал unit-файлы,
ему понадобилось бы право на `daemon-reload` и `LinkUnitFiles`, а такое право
не ограничить одним юнитом — по сути это root. Подробности в
[07-settings-and-systemd.md](07-settings-and-systemd.md).

**Каждая настройка знает, как её применять.** У mpv часть опций меняется на
лету через `set_property` (`audio-device`, `hwdec`...), а часть читается только
при старте (`vo`, `gpu-context`...). Перезапуск делается только тогда, когда без
него не обойтись. Отсюда «set-audio-device без перезапуска».

**Перезапуск сохраняет состояние, неудачный перезапуск откатывается.** Перед
перезапуском сервис снимает снимок состояния. После перезапуска ждёт, пока mpv
снова откроет сокет, и восстанавливает снимок. Если mpv не поднялся с новыми
настройками, возвращаются старые.

**Общение с systemd идёт по D-Bus, а не через `systemctl`.** Это типизированный
API вместо разбора текстового вывода. Права выдаёт polkit-правило, и только на
этот юнит. Оно совместимо с `NoNewPrivileges=`, а `sudo` с ним не работает.

**Закрытые наборы реализаций — это enum, а не trait.** `ServiceManager`,
`CecBackend` и `PowerControl` — перечисления «настоящая реализация | заглушка».
См. [02](02-rust-for-oop-developers.md#интерфейсы-и-полиморфизм).

**Ресурсы с состоянием принадлежат акторам.** Сокет mpv и дочерний процесс mpv
принадлежат каждый своей задаче (task), а остальной код общается с ней через
каналы. Мьютекс вокруг сокета не нужен. См. [04](04-async-and-tokio.md).

## Что сознательно не сделано (пока)

- **OpenAPI.** Справочник API пока написан вручную (`docs/API.md`). В Rust для
  этого есть `utoipa`: схема генерируется из типов и аннотаций. Добавить его
  стоит, когда появится клиент, которому нужна генерация кода.
- **Общий crate для формата снимка.** Тип `PlayerSnapshot` одинаково описан
  здесь и в mpvwatcher. Когда формат устоится, его стоит вынести в отдельный
  crate `remoteplayer-protocol` и подключить в оба проекта как
  git-зависимость.
- **Управление CEC** (включить телевизор, переключить вход, принимать кнопки
  пульта). Пока есть только опрос шины; низкоуровневая часть
  (`cec/linux.rs`) для этого уже готова.
- **TLS.** Для домашней сети его заменяет токен; при выходе наружу нужен
  reverse proxy.
