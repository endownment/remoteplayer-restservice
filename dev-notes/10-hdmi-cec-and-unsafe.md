# 10. HDMI-CEC, ioctl и `unsafe`

## CEC за пять минут

CEC — однопроводная шина поверх HDMI, по которой устройства обмениваются
короткими сообщениями (до 16 байт).

- **Физический адрес** (`1.0.0.0`) — место в дереве HDMI, его выдаёт телевизор
  через EDID. У телевизора `0.0.0.0`. `f.f.f.f` (0xFFFF) — адреса нет:
  телевизор выключен из розетки или кабель не подключён.
- **Логический адрес** (0–15) — роль на шине: 0 — телевизор, 4/8/11 —
  проигрыватели, 5 — аудиосистема, 15 — широковещательный/незарегистрированный.
  Устройство должно **занять** логический адрес, прежде чем задавать вопросы.
- **Сообщение**: первый байт — `инициатор << 4 | получатель`, второй — код
  операции, дальше операнды. Сообщение из одного байта — «опрос» (polling): если
  получатель подтвердил (ACK), устройство с таким адресом есть.

Что делает `GET /cec` (`src/cec/linux.rs`):

1. Открывает `/dev/cec0`, читает возможности адаптера, физический и
   логические адреса.
2. Если логического адреса нет и `claim-logical-address = true`, регистрирует
   Pi как Playback Device. Ядро держит адрес и после закрытия файла.
3. Опрашивает адреса 0–14 (кроме своего).
4. У каждого ответившего спрашивает: `GIVE_PHYSICAL_ADDR` → `REPORT_PHYSICAL_ADDR`,
   `GIVE_OSD_NAME` → `SET_OSD_NAME`, `GIVE_DEVICE_VENDOR_ID` → `DEVICE_VENDOR_ID`,
   `GIVE_DEVICE_POWER_STATUS` → `REPORT_POWER_STATUS`, `GET_CEC_VERSION` →
   `CEC_VERSION`. Ядро само ждёт ответ с нужным кодом (поле `reply`), до
   секунды на вопрос.

Всё это блокирующие вызовы, поэтому они выполняются в `spawn_blocking`.

## ioctl из Rust

Ядро описывает API на C (`include/uapi/linux/cec.h`). В Rust структуры
повторяются один в один:

```rust
#[repr(C)]
struct CecMsg {
    tx_ts: u64,
    rx_ts: u64,
    len: u32,
    ...
    msg: [u8; 16],
    reply: u8,
    ...
}
const _: () = assert!(std::mem::size_of::<CecMsg>() == 56);
```

- `#[repr(C)]` — раскладка полей как у компилятора C (порядок,
  выравнивание, паддинг). Без него Rust вправе переставлять поля.
- `const _: () = assert!(...)` — проверка **во время компиляции**. Если
  размер не совпадёт с ядерным, проект не соберётся, а не испортит память на
  Pi. Ядро кодирует размер структуры в номере ioctl, так что несовпадение
  дало бы `ENOTTY`, а неверный размер был бы куда хуже.
- C-массивы `char[32]` объявлены как `[u8; 32]`: размер и выравнивание
  те же, а знаковость `c_char` различается (на x86 знаковый, на ARM
  беззнаковый) и нам не мешает.
- Структуры инициализируются явными нулями (`CecMsg::directed`, `empty()`),
  без `mem::zeroed()`. Так на одно `unsafe` меньше.

Номера ioctl и обёртки генерирует макрос из крейта `nix`:

```rust
nix::ioctl_readwrite!(cec_transmit, b'a', 5, CecMsg);
// → pub unsafe fn cec_transmit(fd: c_int, data: *mut CecMsg) -> nix::Result<c_int>
```

Это аналог C-макроса `_IOWR('a', 5, struct cec_msg)`.

## Что такое `unsafe` и почему он здесь

`unsafe` не выключает проверки Rust. Он разрешает пять дополнительных
операций, среди которых — вызов `unsafe fn` и разыменование сырого указателя.
Ответственность за корректность переходит на программиста. ioctl — именно
такой случай: мы передаём ядру указатель, и компилятор не видит, что ядро с
ним сделает.

Правило проекта (и общепринятое в Rust): каждый `unsafe`-блок минимален и
снабжён комментарием `// SAFETY:` с объяснением, почему вызов корректен:

```rust
// SAFETY: `message` is a valid `struct cec_msg` that we exclusively borrow for
// the duration of the call; the kernel fills in status fields and, when
// `reply` is set, overwrites `msg`/`len` with the reply in place.
unsafe { cec_transmit(fd, message) }
```

Аргументы корректности одни и те же:

1. указатель смотрит на живой, правильно выровненный объект на стеке;
2. размер объекта равен ядерному (проверено при компиляции);
3. на время вызова у нас эксклюзивный доступ (`&mut`), то есть одновременно
   никто другой его не читает и не пишет;
4. файловый дескриптор открыт: его держит `File`, который живёт до конца
   функции `scan`.

Весь `unsafe` проекта — пять вызовов в одном файле, `src/cec/linux.rs`.
Остальной код от него изолирован безопасными функциями `read_caps`,
`send`, `poll`, `query`.

## Дальше: управление

Для «включить телевизор» (`IMAGE_VIEW_ON` 0x04 + `ACTIVE_SOURCE` 0x82) и
